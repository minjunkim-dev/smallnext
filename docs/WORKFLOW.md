# 협업 방법

## 기본 순서

1. Issue에 해결할 문제나 결정할 질문을 기록합니다.
2. 최신 main에서 짧은 작업 브랜치를 만듭니다.
3. 한 가지 목적의 변경을 커밋합니다.
4. PR에 변경 이유와 검증 결과를 기록합니다.
5. 자동 검사와 필요한 검토 후 squash로 병합합니다.

## 이름

브랜치에는 feat/, fix/, docs/, chore/ 중 하나를 사용합니다.
예: docs/product-hypothesis, feat/current-action-card.
커밋은 변경 내용을 짧게 설명합니다.
예: docs: record planner product hypothesis.

## 검증

문서와 설정 변경은 기본 저장소 검사로 확인합니다.
앱 코드가 생기면 기술 스택에 맞는 lint, 타입 검사, 테스트, 빌드를 추가합니다.
화면 변경은 실제 사용자 흐름과 모션을 직접 확인합니다.
AI 변경은 고정된 목표 예시의 의미와 실행 가능성을 평가합니다.

자동 검사 통과, 앱 빌드, 실제 사용 확인, 배포 완료는 각각 다른 증거입니다.
PR에는 확인한 범위와 확인하지 못한 범위를 구분합니다.

## 작은 프로젝트의 운영

별도 dev 브랜치는 현재 사용하지 않습니다.
main과 짧은 작업 브랜치를 사용합니다.
두 번째 개발자가 참여하면 승인 1개 요구 여부를 검토합니다.
혼자 개발하는 동안 본인 PR에 다른 사람의 승인을 필수로 요구하지 않습니다.

## 보호 규칙

main에는 PR과 자동 검사 통과를 요구하는 보호 규칙을 목표로 합니다.
브랜치 삭제와 강제 푸시는 차단합니다.
실제 강제 적용 여부는 GitHub 계정 요금제와 저장소 설정에서 확인해야 합니다.
지원되지 않으면 위 절차는 작업 규칙이며 기술적인 차단이 아닙니다.

## 비밀정보

API 키, 비밀번호, 서명 파일, 실제 사용자 목표 데이터를 커밋하지 않습니다.
로컬 비밀정보는 무시되는 환경 파일에 저장합니다.
CI에 필요한 비밀정보는 GitHub Secrets에 저장합니다.
운영 자격 증명을 일반 CI 검사에 제공하지 않습니다.
