# 검사 지연 진단 #96

[#96](https://github.com/minjunkim-dev/smallnext/issues/96)의 수동 진단 기록이다.
기준 변경은 [공통 계약 검증](status-contract-validation.md)과 PR #95다.
이 초기 진단에서는 검사 기준을 유지하는 지연 개선을 입증하지 못했다.
빠르게 보인 초기 측정만으로 프롬프트를 변경하지 않았다.
후속 결과는 [출력 오류와 검사 지연 재검증](checker-output-diagnosis.md)에 기록한다.
아래 수치는 작성자의 로컬 수동 측정이다. 저장소 CI의 실행 결과가 아니다.
이 진단 당시 전체 QA 실행기는 저장소에 없었다.
후속 [#97 수동 실행기](oauth-quality-evaluation.md)는 고정 합성 품질 회귀와 같은 보고서 후보의 검사를 다른 checkout에서 재실행한다.
이 문서의 과거 83호출 전체와 모든 로컬 변형을 재현하는 실행기는 아니다.

## 고정 조건과 재현

Claude Code의 기존 `claude.ai` 구독 OAuth를 사용했다.
모든 호출은 `claude-haiku-5-5`, `--effort xhigh`를 요청했다.
CLI의 도구·MCP·hook·세션 저장을 비활성화했다.
토큰을 추출하지 않았다. API 키와 유료 API는 사용하지 않았다.

원래 보고서 입력과 기존 생성 후보 두 개를 고정했다.
[회귀 자료](fixtures/checker-latency-checks.json)에 전체 입력과 후보를 보관한다.
후보는 #94에서 독립 검사로 수용한 실제 합성 출력이다.
예상 판정은 모델에 전달하지 않는다.
입력·후보를 고쳐 성능 개선으로 보고하지 않는다.
공통 계약, 생성 프롬프트, 두 스키마와 다섯 기준을 유지한다.

최소 재현은 생성·DB·화면을 제거한 후보 한 개의 독립 검사다.
첫 재현의 검사 API 시간은 38.990초이고 다음 후보는 51.600초다.
둘 다 `accept`다. 호출당 제공자 메시지는 하나이며 `max_tokens`는 없다.
첫 응답은 1.276초·1.639초에 시작했다.
추론 블록은 36.138초·49.718초까지 이어졌다.
추론 토큰은 8,803개·11,907개다.
CLI 준비와 결과 처리의 전체 추가 시간은 약 1.2~1.3초다.
따라서 생성 재실행, CLI 준비, 출력 한도 복구가 이 재현의 주요 지연 원인은 아니다.
관측한 지연 대부분은 제공자의 추론 블록에 있다.
이 사실만으로 모델 자체의 한계나 반복 추론의 내부 원인을 확정하지 않는다.

수동 피드백 명령은 로컬 QA 자료의 `validation96/run.py replay baseline`이다.
각 실행은 새 디렉터리를 사용한다. 이전 결과를 덮어쓰지 않는다.
품질 일치와 검사 API 중앙값을 함께 출력한다.
30초는 느린 재현을 표시하는 진단 기준이다. 제품 SLA가 아니다.
동일 입력에도 시간이 바뀌므로 실제 개선 판단에는 교차 측정을 사용한다.

아래 시간은 CLI가 보고한 `duration_api_ms`를 초로 바꾼 값이다.
각 행은 같은 원래 입력과 후보 두 개를 한 번씩 검사했다.

마지막 행은 출력 스키마에 기준 1~5의 판정과 근거 필드를 추가한 로컬 대조다.
다른 지시와 원래 입력·후보는 유지했다. 두 출력의 다섯 판정은 모두 pass다.
중앙값은 34.791초다. 작은 표본의 편차를 개선으로 확정하지 않는다.
실제 서비스 스키마에는 이 대조를 반영하지 않았다.

후보 검증 범위 명시는 공통 계약과 모든 기준을 유지했다.
가상의 계획 탐색과 이미 확인한 조건의 반복 검토를 제한하는 역할 지시였다.
이 변형으로 고정 검사 31개를 모두 실행했다.
이 31개 회귀 입력 집합은 위 표의 원래 보고서 후보 두 개와 다른 집합이다.
정상 후보 수용과 잘못된 후보 거절이 31/31 참조와 일치했다.
다섯 기준을 모두 확인한 수용만 성공으로 계산했다.
이 변형의 검사 API 중앙값은 11.330초다. 같은 시점의 기존 지시 대조는 수행하지 않았다.
따라서 이 수치만으로 속도 개선을 주장하지 않는다.
이 합성 회귀는 새로운 holdout이나 일반 품질 실패율을 증명하지 않는다.

## 교차 측정과 변경 취소

초기 측정 후 각 후보의 기존·새 지시를 번갈아 실행했다.
한 후보는 기존→새 순서, 다른 후보는 새→기존 순서를 사용했다.
두 번째 반복에서는 순서를 뒤집었다.
같은 입력·후보·스키마를 사용했다. 판정은 8/8 모두 `accept`다.

| 지시 | 검사 API 4회 | 중앙값 |
| --- | --- | --- |
| 기존 | 35.774 / 34.197 / 43.555 / 33.656초 | 34.986초 |
| 후보 검증 범위 명시 | 49.885 / 37.427 / 37.140 / 29.370초 | 37.284초 |

지시당 4표본의 관측 중앙값은 새 지시가 약 6.6% 길었다.
이 차이는 통계적으로 유의한 퇴보의 증거가 아니다.
초기의 32~35초만 선택하면 잘못된 개선 결론을 내릴 수 있다.
따라서 `check.md` 변경을 되돌렸다.
공통 계약과 실제 실행 경로에 확인되지 않은 최적화를 남기지 않았다.
30초 진단 기준도 일관되게 충족하지 못했다.
최적화 완료로 #96을 닫지 않는다.

## 상태 문장 대조

원래 입력에는 빈 문서라는 설명과 첫 목차 완료 기록이 함께 있다.
진단용 대조에서 `available[1]`의 현재 상태 문장 하나만 바꿨다.
첫 목차가 있는 문서라는 합성 문장으로 바꿨다.
후보와 나머지 입력, 기존 프롬프트는 유지했다.
검사 시간은 30.772초·30.591초이고 판정은 수용 2/2다.
이 측정은 입력이 다르다. 원래 입력의 지연 개선 결과가 아니다.
두 표본만으로 상태 문장이 단독 원인이라고 확정하지 않는다.
실제 문서 상태가 바뀌었다고 주장하지 않는다.
앱의 상태 입력을 임의로 고치지 않는다.
대조에 사용한 문장의 정확한 값은 다음과 같다.

```python
original_request["available"][1] = "현재 상태: 첫 번째 목차 항목이 작성된 보고서 문서가 열려 있다. 나머지 목차 두 개와 핵심 성과 세 줄을 작성하려고 한다."
```

## 검증 경계

기존 프롬프트를 복원하고 실제 Rust 생성·독립 검사 연결 14건을 재실행했다.
모두 독립 검사에서 수용됐고 범위·ID·두 미완료 플래그를 보존했다.
고정 `expected_statuses`와의 일치는 **13/14**다.
이 불일치는 미해결이다. 인수 판정은 #97의 참조 검증 후속으로 남긴다.
`useful-minimum-known`은 `minimum` 참조에 대해 `action`을 반환했다.
상태 참조 원본은 [기존 회귀 자료](fixtures/status-contract-checks.json)의 같은 ID에 있다.
후보는 무거운 책 한 권을 두 손으로 들어 아래 칸에 놓는 행동이다.
입력은 두 손으로 들 수 있다는 사실과 한 손의 막힘을 명시한다.
작성자는 [공통 계약](../../services/api/src/development_ai/contract.md)의 criterion 4에서 `action`이 실제 막힘을 해결하는 경로로 해석했다.
이 해석은 고정 참조 불일치를 통과로 바꾸는 인수 판정이 아니다.
따라서 상태 이름 하나만 보는 참조와 행동 의미의 판정을 구분해야 한다.
예상 값을 실행 후 변경하거나 같은 사례를 재생성해 통과 결과를 고르지 않았다.
원래 `matched=false`와 후보·검사 결과를 보존했다.
전체 고정 참조 14/14 통과로 보고하지 않는다.
이 참조의 의미 검사와 상태 허용 범위는 #97의 재현 평가 후속에서 확인해야 한다.

원래 보고서 입력의 전체 시간은 **67.452초·74.629초**다.
생성 API는 31.752초·24.587초이고 검사 API는 33.562초·47.880초다.
둘 다 `need_info`이며 원래 범위·보류·완료 기록을 보존했다.
이 재검증에서도 약 1분의 응답이 남았다.
14건 전체 시간 중앙값은 19.880초이고 최대는 74.629초다.

진단과 재검증의 완료 역할 호출은 83개다.
83개 모두 실제 `modelUsage`가 `claude-haiku-5-5`였다.
제공자 메시지도 83개다. `max_tokens`는 0개다.
출력 414,080토큰 중 추론은 351,798토큰이다.
추론 원문을 읽거나 저장해서 내부 반복 원인을 확정하지 않았다.
복원한 검사 프롬프트 SHA-256은 `0c31525b0febb63366ee455a0085296c283dbaae55b2a0675e0a5254b4d08160`이다.
회귀 JSON SHA-256은 `1c2ef70d7ac88590d3f517d3557403bb29480e03c2c7f816bd285eb5a1283259`다.
첫 해시는 저장소 `check.md`와 `contract.md`를 `model_instructions`처럼 조립한 UTF-8 바이트다.
둘째 해시는 저장소 JSON의 원본 파일 바이트다. 정규화하지 않았다.
측정 checkout은 UTF-8/LF다. 같은 해시를 재현하려면 같은 파일 바이트를 사용해야 한다.
checkout에서 CRLF로 바꾼 파일은 다른 바이트이므로 같은 해시의 대상이 아니다.
저장소 루트에서 두 해시를 계산할 수 있다.

```python
import hashlib
from pathlib import Path

p = Path("services/api/src/development_ai")
prompt = (p / "check.md").read_bytes() + b"\n" + (p / "contract.md").read_bytes()
print(hashlib.sha256(prompt).hexdigest())
fixture = Path("docs/research/fixtures/checker-latency-checks.json")
print(hashlib.sha256(fixture.read_bytes()).hexdigest())
```

로컬 Rust·격리 PostgreSQL·저장소 검사의 실행 기록은 [PR #98](https://github.com/minjunkim-dev/smallnext/pull/98)에 둔다.
테스트 DB만 제거했다. 기존 개발 DB는 보존했다.
서비스 코드·프롬프트·스키마·피처 플래그에는 최종 변경이 없다.

등록된 피처 플래그 기본값은 모두 OFF다.
원래 입력의 상태·미완료·보류를 유지한다.
자동 수용, 검사 생략, effort 변경과 불필요한 재생성을 추가하지 않았다.
프롬프트 변형은 로컬 QA 디렉터리에만 남겼다.
추론 원문과 인증정보는 수집 결과에 저장하지 않았다.
저장소에는 회귀 자료와 이 진단 기록만 추가한다.
실제 iOS 화면, 실기기, 운영 API의 응답 시간을 재검증하지 않았다.
운영 배포나 모델 준비 승인을 수행하지 않았다.
