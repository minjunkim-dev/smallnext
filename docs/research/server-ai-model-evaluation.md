## 제품 범위와 평가 범위 정정

2026-10-04 사용자 정정: Smallnext는 사용자가 원하는 목표를 현재 실행할 행동으로 나누는 제품이다. 목표 종류를 이력서·포트폴리오로 제한하지 않는다. 제품의 핵심 흐름은 [제품 가설](../PRODUCT.md#핵심-흐름)을 참조한다.
[첫 버전의 대표 목표와 성공 기준](https://github.com/minjunkim-dev/smallnext/issues/3)은 초기 검증 사례다. 제품이 받을 수 있는 목표의 목록이나 경력 관리용 제품 사양이 아니다.
아래 216건은 이력서·포트폴리오라는 한 목표의 합성 사례에서 실행한 시험이다. 서로 다른 목표 216개를 시험한 것이 아니다. 이 결과로 범용 분할 품질을 판단하지 않는다.
고정 사례의 상태 손실·반복·막힘 처리 실패는 재현 자료로 유지한다. 이는 해당 입력·프롬프트 조합의 실패이며, 모델의 모든 목표에 대한 성능 순위가 아니다. 추가 범용 비교는 아래에서 구분한다. 제품 기본 모델의 최종 선택은 미완료다.
개인 경력 문장을 맥 메모 앱에 쓰도록 한 수행 요청은 철회했다. 제품 범위 설명과 평가 절차를 혼동하게 만든 요청이었다. 이를 사용자 시작 실패나 필수 응답 대기로 기록하지 않는다.

공통 모델 지침에는 이력서·역할 문장·PDF 같은 특정 분야의 고정 작업을 넣지 않는다. 목표·완료 조건·사용할 수 있는 자료·제약·현재 막힘·완료 이력·남은 범위는 입력별로 전달한다. 분할과 완료 상태의 원칙은 공통 지침으로 유지한다.
1차 범용 점검은 목표 6종의 첫 행동과 재분할 2회, 후보 2개로 36요청이다. 별도의 정보 부족·이미 완료·작은 행동만 완료 경계를 각 후보에 1회씩 더해 총 42요청을 실행했다. 이 수치는 검사 범위이며 품질 통과선이 아니다.
범용 점검에서 실패를 찾으면 해당 목표와 실패 원인을 고정 회귀 사례에 추가한다. [목표 분할 결과의 확정 품질 기준](https://github.com/minjunkim-dev/smallnext/issues/6#issuecomment-5968651172)의 기존 반복·경계 사례도 유지한다. 첫 검증 사례를 통과했다고 범용성을 주장하지 않는다.
범용 프롬프트로 수정한 뒤 `general-subscription-v1`이라는 새 판으로 실행했다. 과거 프롬프트의 시간·품질을 새 판의 결과로 사용하지 않는다. 기존 구독으로 42건을 추가했다. 일반 개발자 API 키 요청은 여전히 0건이다.
사용자의 실제 수행은 제품 흐름과 검토 방법을 구체화한 뒤 별도로 확인한다. 지금 개인 경력 작업을 수행할 필요는 없다. AI 보조 검토·사람의 출력 검토·사용자의 실제 시작 증거를 구분한다.

연구 판단: 후속 회귀 비교의 기준 후보는 Sonnet 5.5로 제안한다. 이 세트에서 Luna의 재분할 실패를 확인했고, Sonnet의 주요 첫 행동은 목표에 맞는 구체적인 결과였다. 이는 단일 예비 흐름의 판단이며 범용 성능 순위나 제품 기본 모델 확정이 아니다.
Luna는 정상 토큰 요율이 낮은 비용 대안으로 유지한다. 후속 선택은 재분할 개선과 필수 기준 검토, 실제 서버 API 비용·지연을 함께 확인해야 한다. 가격으로 실패를 상쇄하지 않는다.
다음 검증은 최소 행동의 한계 처리, 재분할의 실제 장애 감소, 행동과 완료 조건의 일치를 보완한 뒤 같은 범용 세트와 기존 고정 회귀 세트를 새 판으로 실행하는 것이다. 사용자에게 개인 경력 과제를 요구하지 않는다.

### 범용 반복·기존 회귀 재시험과 추천안

2026-10-05에 `repeated-goal-evaluation-v1`을 마쳤다. 후보별 117요청, 총 234요청이다. 범용 6목표의 첫 행동·재분할 2회를 각 3회 반복해 54요청, 경계 3종을 각 3회 반복해 9요청을 실행했다. 범용 세트는 후보별 63요청이다. 기존 대표 목표의 고정 회귀 54요청도 후보별로 실행했다.
이 판을 포함한 고정 평가 요청은 492건이다. 예비 시험 2건은 별도다. 요청 수를 서로 다른 목표 수나 실제 사용자의 수행 수로 확대하지 않는다.

공통 지침에 허용된 수행 단위, 대안별 완료 조건 일치, 현재 막힘 유지, 새 결과, 실제 장애 감소, 정직한 최소 한계를 명시했다. 특정 분야의 답이나 예상 답은 입력에 넣지 않았다.
걷기 입력에는 사용할 수 있는 2분 타이머를 추가했다. 기존 대표 목표의 메모는 새로 쓸 수 있는 빈 메모로 명확히 했다. 이 두 입력 보완 때문에 이전 판과 완전히 같은 입력의 비교라고 주장하지 않는다. 새 판 안에서는 후보 두 개가 같은 입력·스키마·공통 지침과 3회 반복 조건을 받았다.

## 합성 평가 입력 검토안

상태: 2026-10-04 사용자가 비교 진행을 승인했습니다. 예비 시험 뒤 같은 합성 상황으로 구독 CLI 반복 평가를 진행했습니다.
이 문서는 연구와 평가 기록입니다. 제품 기본 모델의 확정 답은 아닙니다.

기준은 [목표 분할 결과를 어떤 기준으로 통과시킬 것인가?](https://github.com/minjunkim-dev/smallnext/issues/6#issuecomment-5968651172)와 [첫 버전의 AI 연결 방식과 실패 시 동작은 무엇인가?](https://github.com/minjunkim-dev/smallnext/issues/10#issuecomment-5969227418)입니다.

### 공통 입력

아래 문장은 평가를 위한 합성 입력입니다. 실제 개인·회사 원문을 복사하지 않았습니다. 공개된 결정의 목표 구조와 경험 A의 종류만 사용합니다.

```text
목표: 준비 시작일부터 3주 안에 지원용 이력서 PDF 하나와 포트폴리오 PDF 하나,
대표 공개 저장소 1~2개와 기존 안내 페이지 하나를 정리한다.
완료 조건: 두 PDF의 경험·기간·역할이 서로 일치하고,
선택한 저장소의 설명 및 안내 페이지에서 자료를 확인할 수 있다.
이번 행동의 대상: 경험 A, iOS 빌드 환경 분리.
합성 원고: 경험 A의 제목만 있다. 실제 역할·수치·성과는 아직 확인하지 않았다.
사용할 수 있는 자료: 이 합성 원고와 앱에 남길 짧은 메모.
사용할 수 없는 자료: 원본 회사 문서, 비공개 저장소, 성과 측정 기록.
기본 제약: 링크를 읽었다고 가정하지 않는다. 없는 역할·성과·수치를 만들지 않는다.
현재 행동과 최종 목표의 완료를 구분한다.
```

이 입력은 실제 원고의 내용이나 경험 A의 역할을 확정하지 않습니다.
공급자에게 이름, 회사명, 연락처, 파일 경로, 저장소 주소와 문서 원문을 보내지 않습니다.

## 구독 고정 평가: 실행 조건과 판정

사용자 승인 뒤 `subscription-v1`을 실행했다. 다섯 상황은 각 3회 반복했다. 각 흐름은 첫 행동과 재분할 2회로 구성했다. 경계 3종은 각 3회 실행했다. 후보별 54요청이다.
두 후보는 같은 합성 입력과 JSON Schema를 받았다. 예상 답과 채점표는 입력에 넣지 않았다. 재분할에는 이전 제안과 아직 시작하지 않았다는 고정 피드백을 전달했다.
출력 필드는 `status`, `action`, `completion_condition`, `estimated_minutes`, `reason`, `remaining_work`, `goal_completed`, `current_action_completed`, `preserved_completed_ids`다. 분 단위 시간은 모델의 추정이며 사용자 수행 시간이 아니다.
새 제안은 미실행 상태다. 남은 역할 문장·기간·두 PDF·저장소·안내 페이지를 모두 유지해야 한다. 완료 경계에서는 `role-mark` 자기 보고만 보존한다.

Codex CLI 0.160.0과 Claude Code 2.1.289를 사용했다. 두 후보 모두 `low` 추론 설정이다. 요청별 CLI 세션을 새로 만들었다. 공급자별 순차 실행, 공급자 간 병렬 실행이다.
Codex는 사용자 설정을 무시하고 전용 모델 지침 파일과 출력 스키마를 지정했다. 읽기 전용 sandbox를 사용했다. 셸·파일 변경·웹 검색·이미지 도구를 껐다. 스킬 설명 예산은 1토큰으로 지정했다.
Claude는 safe/restricted 모드, 빈 도구 목록, 빈 MCP 설정, 설정 소스 없음, slash command 없음, 세션 저장 없음으로 실행했다. `--bare`는 구독 OAuth를 읽지 않으므로 쓰지 않았다.
하네스 timeout은 120초다. timeout·CLI 오류·관찰된 외부 도구 실행은 해당 후보 실행을 중단한다. 하네스 재시도는 0회, 요청한 모델 전환은 없다. CLI 내부의 전송 재시도 횟수는 확인하지 않았다.
API 키와 별도 공급자 경로 환경 변수는 자식 프로세스에서 제외했다. 저장된 공식 CLI 구독 로그인을 사용했다. OAuth 토큰을 읽거나 서버로 복사하지 않았다.

## 2026-10-05 현재 막힘 명시 실험

같은 구독 승인 범위에서 검증용 지침과 입력 구성을 보완했다. 제품 코드는 구현하지 않았다. 목표 종류를 제한하지 않았고, 개인 경력 작업이나 새 API 키를 요청하지 않았다.
검사할 가정은 ‘모델이 현재 막힘보다 남은 목록의 첫 항목을 우선한다’였다. 단독 원인으로 확정하지 않고, 지침 변경과 입력 위치 변경을 나누어 관찰했다.

### 사전 대조와 전수 실행

`focused-subscription-v1`은 공통 지침의 우선순위만 바꿨다. 대상 이름·현재 막힘·남은 목록을 구분했다. 기존 사실과 입력 구성을 유지했다. 성과 근거 부족·수행량 부담·여행 선택의 첫 행동을 각 3회 요청했다.
자동 검사 9건은 통과했다. 성과 근거 부족의 3회 모두 역할 작성으로 우회했다. 지침 문구만 강화하면 해결된다는 가정은 이 사전 시험에서 지지되지 않았다.

`focused-subscription-v3`은 같은 수정 지침과 사실을 유지했다. 기존 `context.situation`을 사용자 `request` 앞에 ‘지금 해결할 막힘’으로 다시 명시했다. 예상 정답과 특정 근거 종류는 입력에 추가하지 않았다. 동일 9건을 실행했다.
성과 근거 부족의 첫 행동 3회 모두 근거 처리로 바뀌었다. 1회는 확인할 기록 종류를 골랐다. 2회는 근거 없는 수치를 쓰지 않는 처리 정책을 정했다. 역할 작성 우회는 0회였다. 정책 선택을 필요한 기록 종류 선택과 같은 결과로 판정하지 않는다.

## 생성기와 검사기 네 조합의 전체 경로 비교

### 고정 조건과 실제 적용 상태

범용 6목표, 기존 합성 목표의 5상황, 두 세트의 완료·준비·정보 부족 6경계를 각각 3회 반복한다. 조합별 51흐름, 전체 204흐름이다. 한 흐름은 첫 제안과 재분할 2회까지 포함한다. 모든 제안이 수용되면 최대 468판정과 936모델 요청이다. 서로 다른 204목표가 아니다.

각 조합은 독립 생성과 독립 상태를 가진다. 원래 맥락·남은 목록·완료 이력은 보존한다. 구조 검사를 통과한 후보만 의미 검사에 보낸다. 수용한 후보만 해당 흐름의 `previous_outputs`에 넣는다. 거부·판정 불가·오류이면 그 흐름을 중단하고 직전 상태를 유지한다. 자동 재생성과 거부 답에 대한 후속 재분할은 0회다. 수용한 `need_info`도 사용자 답변 대기로 종료한다. 합성 답변을 만들어 다음 단계로 진행하지 않는다.

첫 제안의 입력은 네 조합에서 동일하다. 이후 입력은 각 조합이 수용한 실제 후보를 포함하므로 달라질 수 있다. 같은 후보에 대한 검사기 비교는 별도 대조로 분리했다. 기존 정상·실패 참조 22개와 판정이 엇갈린 3개를 두 검사기에 각 1회 보냈다. 총 50요청이다. 참조 정답·후보 ID는 검사 입력에 넣지 않는다. 참조는 AI 보조 판정이며 사람 정답이 아니다. 예전 미사용 12사례도 이 대조에 포함되므로 새로운 미지 평가라고 부르지 않는다.

### 비용 계산 조건

API 청구와 제품 서버 지연은 측정하지 않는다. 시간은 해당 조합의 생성 CLI와 검사 CLI를 순서대로 실행한 전체 경과 시간이다. CLI 초기화·구독 라우팅·스키마 처리와 병렬 부하를 포함한다. API 성능 순위로 확대하지 않는다.

## 2026-10-05 반복 막힘 질문 선택 후 재검토

## 2026-10-05 직접 질문 검사 대조

사용자가 선택한 질문 기준을 검사 지침에 반영한 뒤, 기존 구독으로 제한 대조 `direct-question-v1`을 실행했다. 행동 생성·자동 재생성·제품 적용·일반 개발자 API 요청은 없다. [확정 재분할 정책](https://github.com/minjunkim-dev/smallnext/issues/5#issuecomment-5968343988)과 [의미 검사 처리](https://github.com/minjunkim-dev/smallnext/issues/40#issuecomment-5982135283)는 유지한다.

이전 `contract-v3` 보완 검사 지침을 기준 구성으로 사용했다. 새 구성에는 반복 막힘에서 첫 실제 장애를 직접 묻고, 필요한 정보의 분석을 사용자에게 요구하는 질문은 거부하는 규칙만 추가했다. 입력·후보·schema·low 설정·CLI 호출 방식은 그대로다. 최초 단계의 근거 기록 종류 선택은 금지하지 않았다. 지침과 후보는 호출 전에 동결했으며 중간 수정·추가 호출은 없다.

미흡한 정보 분석 질문과 직접 첫 장애 질문은 같은 원래 요청을 사용한다. 직접 질문 후보만 행동 문장·완료 조건·이유를 바꿨고 나머지 상태와 기록은 같다. 기존 질문 참조 하나는 사용자 선택을 반영한 거부다. 새 직접 질문의 전체 입력 적합성과 다른 참조는 여전히 보조 판단이다. 어느 후보의 실제 수행이나 전체 품질도 사람이 승인하지 않았다.
