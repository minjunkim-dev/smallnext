# 현재 행동 화면의 모바일 모션·접근성 근거

- 조사 티켓: [Issue #7](https://github.com/minjunkim-dev/smallnext/issues/7)
- 확인일: **2026-10-03**. 아래 출처는 모두 이 날짜에 확인했습니다.
- 범위: 본인의 업무·학습·개인 프로젝트. 휴대폰에서 현재 행동 하나를 봅니다.
- 흐름: `현재 행동 → 더 작게 → 분할 결과`, `현재 행동 → 완료 → 다음 행동`.
- 상태: 첫 버전 사양의 결정 근거입니다. 화면과 모션을 확정하지 않습니다.

## 증거의 구분

**기준 사실**은 Apple 지침과 W3C 기준의 내용입니다.
**제품 설명**은 제작사가 공개한 기능 설명 또는 제작 기록입니다.
**직접 관찰**은 실제 앱을 조작한 결과입니다. 이번 조사에는 이 증거가 없습니다.
**설계 제안**은 Smallnext에서 검증할 후보입니다. 기존 제품의 구현 사실이 아닙니다.

제품의 소개 문구는 사용성·성능·만족도의 검증 결과로 사용하지 않습니다.
웹 문서의 확인과 실제 앱의 실행 검증을 구분합니다.

## Apple에서 확인한 기준 사실

Apple HIG는 설계 지침입니다. WCAG의 A·AA·AAA 적합 수준과 같은 등급이 아닙니다.

| 공식 출처 | 확인한 사실 | 다음 결정에 주는 함의 |
| --- | --- | --- |
| [HIG: Motion](https://developer.apple.com/design/human-interface-guidelines/motion) | 모션은 목적이 있어야 합니다. 중요한 정보의 유일한 전달 수단으로 쓰지 않습니다. 피드백은 짧고 정확해야 합니다. 빈번한 조작의 불필요한 모션과 완료까지의 대기를 피합니다. 가능한 경우 모션을 취소할 수 있게 합니다. | 분할·완료의 의미를 먼저 정합니다. 반복할 때 늘어나는 대기 시간을 측정합니다. |
| [HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) | Reduce Motion이 켜지면 자동·반복 모션, 확대·축소와 주변부 움직임을 줄입니다. 이동 전환을 페이드로 바꾸고, 튕김과 깊이 변화·블러 애니메이션을 줄이는 방법을 제시합니다. | 모션 감소 버전을 별도로 검토합니다. 같은 행동 결과와 정보가 남아야 합니다. |
| [HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) | iOS·iPadOS 표는 **기본 제어 크기 44×44pt**, **최소 제어 크기 28×28pt**를 구분합니다. 제어 사이의 여백도 중요합니다. 자주 쓰는 조작에는 단순한 제스처를 쓰고 화면상의 대안을 제공합니다. | 핵심 버튼은 기본 크기부터 검토합니다. 분할 시 버튼이나 터치 영역을 줄이지 않습니다. |
| [VoiceOver 평가 기준](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/voiceover-evaluation-criteria) | 제어에는 간결하고 정확한 레이블이 필요합니다. 화면이 바뀌면 커서는 새 내용으로 논리적으로 이동해야 합니다. 보이지 않는 내용으로 이동하면 안 됩니다. 일반 탭과 VoiceOver 활성화는 같은 동작을 해야 합니다. | 다음 행동의 읽기 위치와 버튼 동작을 검증합니다. 사라진 카드에 포커스를 남기지 않습니다. |

HIG 본문은 조사 도구에서 JavaScript 안내만 표시했습니다.
위 HIG 사실은 Apple이 제공하는 현재 문서 데이터의 본문으로 확인했습니다.
확인일은 2026-10-03입니다: [Motion 원문 데이터](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json), [Accessibility 원문 데이터](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/accessibility.json).

## W3C에서 확인한 기준 사실

[WCAG 2.2](https://www.w3.org/TR/WCAG22/)는 웹 콘텐츠의 접근성 기준입니다.
아래 표는 이 흐름에 관련된 일부 기준입니다. 전체 적합성 검사 목록이 아닙니다.
네이티브 앱에서는 플랫폼 접근성 기능과 함께 설계 근거로 사용합니다.
W3C의 Understanding 문서는 기준을 해설합니다. 해설의 예시가 별도 필수 구현은 아닙니다.

| 기준과 공식 해설 | 수준 | 확인한 사실 | 다음 결정에 주는 함의 |
| --- | --- | --- | --- |
| [2.3.3 Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) | **AAA** | 조작으로 시작하는 이동 애니메이션은 끌 수 있어야 합니다. 기능이나 정보에 필수인 경우는 예외입니다. | 카드 분할·이동을 필수로 단정하지 않습니다. 모션 없는 대안을 검토합니다. 이 기준을 AA 요구로 표기하지 않습니다. |
| [2.2.2 Pause, Stop, Hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html) | **A** | 자동 시작하고 5초를 넘으며 다른 내용과 함께 표시되는 이동·깜박임·스크롤에는 일시 정지·중지·숨김 수단이 필요합니다. 필수 활동은 예외입니다. 자동 갱신에는 별도 조건이 있으며 5초 예외가 없습니다. | 버튼으로 시작하는 짧은 전환의 일반 시간 상한으로 해석하지 않습니다. 장식 반복이나 자동 다음 행동을 넣으면 적용 조건을 다시 확인합니다. |
| [2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) | **AA** | 포인터 대상은 최소 24×24 CSS px입니다. 작은 대상 주변의 24 CSS px 원이 인접 대상·원과 겹치지 않는 간격 예외 등이 있습니다. | 핵심 조작의 실제 터치 영역을 검사합니다. Apple의 pt와 CSS px를 같은 수치 단위로 취급하지 않습니다. |
| [2.5.5 Target Size (Enhanced)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html) | **AAA** | 최소 44×44 CSS px입니다. 동등한 제어·문장 내부·사용자 에이전트 제어·필수 표현의 예외가 있습니다. | 44 CSS px를 AA 최소값으로 적지 않습니다. 큰 핵심 버튼의 추가 기준 후보로 검토합니다. |
| [2.5.1 Pointer Gestures](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html) | **A** | 여러 포인터나 경로 기반 제스처로 작동하는 기능은 단일 포인터로도 작동해야 합니다. 필수인 경우는 예외입니다. | 핀치·스와이프 패턴을 도입하면 버튼 등 대안을 검토합니다. |
| [2.5.2 Pointer Cancellation](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html) | **A** | 누르는 순간 기능을 실행하지 않거나, 놓는 순간의 완료에 취소·되돌리기를 제공하는 등 기준의 조건 하나를 충족해야 합니다. 필수 동작은 예외입니다. | 잘못 누른 완료를 취소할 수 있는지 검토합니다. 손가락을 놓기 전에 다음 행동으로 바꾸지 않는 후보를 시험합니다. |
| [2.4.3 Focus Order](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) | **A** | 의미·조작에 영향을 주는 순차 탐색의 포커스 순서는 의미와 조작 가능성을 보존해야 합니다. | 카드 교체 후 탐색 순서가 이어져야 합니다. |
| [2.4.7 Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html), [2.4.11 Focus Not Obscured (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) | **AA** | 키보드 포커스 표시를 볼 수 있어야 합니다. 포커스를 받은 제어가 제작한 콘텐츠에 완전히 가려지면 안 됩니다. | 움직이는 카드나 완료 효과가 포커스 제어를 가리는지 검사합니다. |
| [4.1.2 Name, Role, Value](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) | **A** | 제어의 이름·역할·상태·값을 프로그램으로 파악할 수 있어야 합니다. 상태·값의 변경도 보조 기술에 전달해야 합니다. | 시각 효과와 별도로 완료 상태와 제어의 의미를 제공합니다. |
| [4.1.3 Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) | **AA** | 포커스를 받지 않는 상태 메시지는 역할·속성 등을 통해 보조 기술이 전달할 수 있어야 합니다. 모든 새 콘텐츠가 상태 메시지는 아닙니다. | 완료·분할 결과·대기·오류의 상태 알림과 다음 행동 본문을 구분합니다. |

**사양 결정 후보:** 웹 구현이면 관련 A·AA 기준을 기본 검토 대상으로 삼습니다.
조작 모션 해제는 AAA 기준과 Apple 지침에 근거한 추가 요구 후보로 기록합니다.
이 표만으로 앱의 WCAG 적합 수준을 선언하지 않습니다.

## 의미 전달과 전환의 설계 제안

아래 내용은 공식 기준에서 도출한 후보입니다. 최종 UI 결정은 아닙니다.

| 전환 | 전달해야 할 의미 | 검토할 제약 |
| --- | --- | --- |
| 더 작게 | 같은 일을 더 작은 행동으로 바꿨습니다. 완료 처리가 아닙니다. | 조각이 사라질 때 다른 할 일이 삭제됐다고 오해하지 않아야 합니다. 이전·새 행동의 내용으로 관계를 설명할 수 있어야 합니다. |
| 완료 | 현재 행동이 완료 상태가 됐습니다. | 완료 반응과 다음 행동 표시를 구분합니다. 처리 중·실패 상태를 성공 효과로 표시하지 않습니다. |
| 다음 행동 | 현재 할 대상이 바뀌었습니다. | 새 내용을 읽고 조작할 수 있어야 합니다. 이전 행동의 포커스·접근성 요소가 남으면 안 됩니다. |

카드가 움직여도 핵심 제어의 터치 영역은 안정적으로 유지하는 후보를 시험합니다.
한 번의 탭이 새 행동의 완료까지 이어지는 오류를 막는 기준을 검토합니다.
짧은 입력 피드백과 실제 처리 지연을 구분합니다. 모션으로 처리 지연을 숨기지 않습니다.
모션 종료를 기다려야 하는 구간과 실제 처리 대기 구간을 따로 측정합니다.

반복 비용은 `반복 횟수 × 모션 때문에 추가된 조작 불가 시간`으로 기록합니다.
예를 들어 0.3초 대기를 20회 강제하면 6초가 추가됩니다. 이 값은 계산 예시입니다.
이번에 확인한 지침은 이 흐름에 150ms 또는 300ms 같은 고정 시간을 지정하지 않습니다.
시제품에서 정보 이해와 반복 비용을 함께 비교한 후 시간을 정합니다.

모션 감소 후보에서는 분할·이동·확대·회전을 제거하거나 정적인 교체·짧은 페이드로 바꿉니다.
완료 상태, 새 행동, 처리 결과와 조작 가능성은 기본 버전과 같아야 합니다.
소리·햅틱은 추가 피드백 후보입니다. 이 수단만으로 변경 의미를 전달하지 않습니다.

## 스크린리더와 상태 알림의 설계 제안

‘완료됨’, ‘분할 중’, ‘분할 실패’처럼 결과·대기·오류를 알리는 메시지는 상태 알림 후보입니다.
다음 행동 본문을 교체했다는 이유만으로 화면 전체를 라이브 영역으로 만들지 않습니다.
새 화면으로 이동했거나 포커스를 옮겼다면 상태 메시지와 별도 상황입니다.
이는 [4.1.3 공식 해설](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)의 적용 범위에서 도출했습니다.

웹이면 [ARIA22](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA22)의 `role="status"`를 후보로 검토합니다.
이 역할은 기본적으로 `polite` 알림을 사용합니다. 이는 가능한 구현 기법이며 필수 API는 아닙니다.
네이티브 앱이면 플랫폼 접근성 상태·알림 기능을 사용해 같은 의미를 전달해야 합니다.
구현 방식은 기술 스택을 정한 후 결정합니다.

키보드 포커스와 스크린리더 탐색 위치를 각각 시험합니다.
기존 제어에 위치를 유지할지 새 행동의 시작으로 이동할지는 화면 구조에 따라 결정합니다.
완료 알림과 새 행동 읽기가 겹치거나 같은 내용을 두 번 읽지 않도록 검토합니다.
포커스를 받은 내용은 접근성 탐색에 존재해야 합니다. 장식 조각은 탐색 대상에서 제외하는 후보입니다.

## 시제품에서 확인할 항목

| 시험 | 확인할 결과 |
| --- | --- |
| 일반 모션·모션 없음·모션 감소 비교 | 분할과 완료를 구분할 수 있는가? 어떤 일이 남았는지 설명할 수 있는가? |
| 분할·완료를 20회 반복 | 추가 대기 시간, 조작 실패, 효과에 대한 피로를 기록합니다. 20회는 시험 제안이며 공식 기준이 아닙니다. |
| 전환 중 빠른 연속 탭·탭 취소 | 중복 완료, 잘못된 다음 행동 완료, 사라진 버튼 조작이 없는지 확인합니다. |
| 작은 화면·큰 글자·한 손 조작 | 행동과 완료 조건을 읽을 수 있는지 확인합니다. 핵심 제어의 크기·간격·위치를 검사합니다. |
| OS 모션 감소 설정 변경 | 설정을 반영하는지 확인합니다. 효과를 줄여도 같은 결과와 조작이 남는지 확인합니다. |
| VoiceOver·사용 가능한 다른 스크린리더 | 행동 본문, 제어 레이블, 완료·대기·오류를 이해할 수 있는지 확인합니다. 분할과 다음 행동으로 이어지는지 시험합니다. |
| 키보드·플랫폼 보조 입력 | 포커스 순서·표시·가림을 검사합니다. 일반 탭과 같은 작업을 수행하는지 확인합니다. |
| 지연·실패·결과 없음 | 성공 효과가 먼저 나오지 않는지 확인합니다. 새 행동이 없을 때 완료 사실과 현재 상태를 전달하는지 시험합니다. |

앱별 현재 버전의 모션 시간, 프레임 성능, 모션 감소, 스크린리더 동작을 검증하지 않았습니다.
제작사의 만족·집중 향상 주장, AI 분할 품질, 사용자의 선호를 입증하지 않았습니다.
Llama Life 기능 페이지는 직접 열기에서 본문이 추출되지 않아 공식 검색 색인의 본문과 시작 안내로 확인했습니다.
따라서 모바일 앱의 현재 세부 동작과 동일하다고 보장하지 않습니다.
